Common WordPress Security Mistakes

The most frequent WordPress security mistakes we see — and exactly how to fix each one with our WordPress hardening checklist.

Published: May8, 2026 · Reading time: 11 minutes

WordPress makes it easy to build a website, but that same ease of use leads many site owners to make predictable security mistakes. In our experience auditing hundreds of WordPress sites, the same errors appear again and again. The good news: every one of these WordPress security mistakes is fixable once you know about it.

1. Using "admin" as the Username

This is the oldest mistake in the book, yet it remains one of the most common. The default administrator username in WordPress used to be "admin." Attackers know this, and they specifically target the "admin" username in brute force attacks. If your username is "admin," you have already given attackers half of your login credentials.

The fix: Create a new administrator account with a unique username, log in as the new user, and delete the old "admin" account. Assign all content from the old account to the new one.

2. Weak Passwords on Administrator Accounts

Even with a strong username, a weak password makes your site vulnerable. We frequently see administrator passwords that are dictionary words, simple patterns, or reused across multiple sites. With modern password cracking tools, a weak password can be broken in seconds.

The fix: Use a password manager to generate and store complex passwords. A strong WordPress password should be at least 16 characters with a mix of uppercase, lowercase, numbers, and symbols. Better yet, enable two-factor authentication using a plugin like Wordfence or WP 2FA.

3. Not Limiting Login Attempts

By default, WordPress allows unlimited login attempts. This means an attacker can write a script to try thousands of password combinations against your login page. Without rate limiting, a brute force attack is trivial to execute.

The fix: Install a login limit plugin like "Limit Login Attempts Reloaded" or use a web application firewall (like Cloudflare or Wordfence) that provides brute force protection at the network level. Our WordPress hardening guide recommends a maximum of 3-5 login attempts before a temporary lockout.

4. Keeping Default wp-admin and wp-login Paths

Every WordPress site has its login page at /wp-login.php or /wp-admin/. Attackers know this and target these paths specifically. While changing the login URL is not a silver bullet, it reduces noise from automated bots and makes scripted attacks less efficient.

The fix: Use a plugin like "WPS Hide Login" to change the login URL to something unique. Just make sure to write down the new path — there is no "forgot login URL" button.

5. Installing Too Many Plugins

Every plugin you install increases your attack surface. Each plugin is additional code that could contain vulnerabilities. We regularly audit sites with 40, 50, or even 80 plugins installed — many of them inactive but still present on the server.

The fix: Audit your plugins regularly. Delete any that you are not actively using. Replace multiple plugins with a single plugin that accomplishes the same task. Question whether you really need each plugin before installing it.

6. Using Nulled (Pirated) Themes and Plugins

Some site owners download "nulled" (pirated) premium themes and plugins to avoid paying for them. This is one of the most dangerous things you can do. Nulled software is frequently modified to include backdoors, malware, or SEO spam. Even if the file appears clean initially, it cannot be trusted.

The fix: Only install themes and plugins from the official WordPress repository or reputable commercial developers. If budget is a concern, there are excellent free alternatives to most premium plugins.

7. Not Updating WordPress, Themes, and Plugins

We cannot count how many sites we have audited that are running WordPress versions from two or three years ago. Every update includes security fixes. When you skip updates, you are leaving known vulnerabilities unpatched and advertised to the world.

The fix: Enable automatic updates for WordPress core (minor releases) and consider auto-updates for plugins as well. At minimum, check for updates weekly. Our WordPress security checklist includes a monthly update review process.

8. Leaving XML-RPC Enabled

XML-RPC is a feature that allows external services to connect to your WordPress site. While it has legitimate uses (like the WordPress mobile app), most small business sites do not need it. Leaving it enabled gives attackers a way to perform brute force attacks more efficiently, since XML-RPC allows multiple authentication attempts in a single request.

The fix: If you do not need XML-RPC, disable it by adding a rule to your .htaccess file or using a plugin like "Disable XML-RPC."

9. Allowing File Editing from the WordPress Dashboard

By default, WordPress allows administrators to edit theme and plugin files directly from the dashboard. This is convenient for developers but dangerous from a security perspective. If an attacker gains admin access, they can inject malicious code into your files without needing FTP or server access.

The fix: Add define('DISALLOW_FILE_EDIT', true); to your wp-config.php file. This disables the file editor while still allowing plugin/theme installation.

10. Using the Default Table Prefix

Many WordPress installations still use the default "wp_" table prefix. This is well-known and makes SQL injection attacks easier to execute because the attacker already knows the table names. A secure installation uses a custom prefix.

The fix: For new installations, choose a custom table prefix during setup. For existing sites, use a plugin like "Change Table Prefix" or do it manually via phpMyAdmin. Always back up your database first.

Your WordPress Security Checklist

Use this WordPress security checklist to review your site:

  • Change default "admin" username
  • Use strong, unique passwords for all accounts
  • Enable two-factor authentication
  • Limit login attempts
  • Change default login URL
  • Remove unused plugins and themes
  • Update WordPress core, plugins, and themes regularly
  • Disable XML-RPC if not needed
  • Disable file editing from dashboard
  • Use a custom database table prefix
  • Install a security plugin (Wordfence, Sucuri, or similar)
  • Set up automated backups stored offsite
